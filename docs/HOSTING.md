# Хостинг и домен

Боевой адрес сайта — **https://flushot.ink**. Страница обслуживается nginx на своём сервере;
копия на GitHub Pages остаётся как резервная.

## Сервер

| Параметр | Значение |
|---|---|
| Тариф | NL, Ryzen 9 9950x, 1 vCore, 1 ГБ DDR5, 10 ГБ NVMe, 100 Мбит/с |
| ОС | AlmaLinux 8.10, ядро 4.18 |
| IP | `78.17.32.87` |
| Имя хоста | `flushot.ink` |
| Веб-сервер | nginx 1.14.1, 80 и 443, сертификат Let's Encrypt |
| Корень сайта | `/var/www/flushot.ink` — символическая ссылка на текущий выпуск |

Что установлено дополнительно к базовой системе: `nginx`, `tar`, `certbot` с плагином
`python3-certbot-nginx`, репозиторий EPEL. SELinux выключен, firewalld включён и открывает
только `http`, `https` и `ssh`.

Сервер обслуживает один сайт, поэтому порт 80 по умолчанию перенаправляет на
`https://flushot.ink`, а `www.flushot.ink` — туда же: один адрес страницы, без дублей в поиске.

## Как обновить сайт

Сайт не заливается вручную с рабочей машины: источник правды — ветка `main` репозитория.
Скрипт `deploy/deploy-site.sh` скачивает архив репозитория и выкладывает `site/`:

```bash
ssh root@78.17.32.87
bash /root/deploy-site.sh          # ветка main
bash /root/deploy-site.sh v2.2.8   # или конкретный тег
```

Скрипт и конфиги лежат в репозитории, в папке `deploy/`; на сервере они просто скопированы.
После правки скрипта его нужно положить обратно:

```bash
scp deploy/deploy-site.sh root@78.17.32.87:/root/deploy-site.sh
```

Порядок внутри скрипта важен, и вот почему:

1. Архив распаковывается во временный каталог, `site/` копируется в
   `/var/www/releases/flushot.ink-<дата>`. Пока это происходит, живой сайт не тронут.
2. Из копии удаляется `КАК ОПУБЛИКОВАТЬ.txt` — это инструкция для того, кто правит страницу,
   а не страница.
3. Две проверки: `index.html` не пустой и содержит строку `flushot.ink`. Вторая ловит
   типичную ошибку «задеплоил не ту ветку»: страница с чужим canonical уже уехала бы на боевой
   домен.
4. Символическая ссылка `/var/www/flushot.ink` переключается одной операцией `mv -T`. Сайт
   никогда не бывает наполовину залитым: nginx либо видит старый каталог целиком, либо новый.
5. Три последних выпуска остаются на диске.

После выкладки стоит прогнать проверку живой страницы — она идёт с рабочей машины и смотрит
на то, что реально отдаёт сервер:

```bash
npm run verify:live            # https://flushot.ink/
npm run verify:live -- <url>   # любой другой адрес
```

### Почему ссылки на файлы содержат `?v=`

Браузер кеширует `styles.css` надолго, и без хеша в адресе правка внешнего вида доезжала бы
до разных устройств в разное время: у одного в кеше старая версия, у другого новая, и одна и
та же страница выглядит как две разные. Поэтому каждая ссылка на файл несёт хеш его
содержимого:

```html
<link rel="stylesheet" href="styles.css?v=8ecff7f0">
```

Восемь символов — начало SHA-256 файла. Хеш считается по `site/`, коммитится вместе с правкой
и проверяется в `npm run verify:site`: если файл изменился, а хеш в ссылке старый, проверка
падает. Обновить хеши после правок:

```bash
npm run stamp
```

Сервер после этого может отдавать файлы с `immutable` на год: изменившийся файл получает новый
адрес, а старый адрес больше никто не запрашивает. Сам `index.html` не кешируется — именно он
и приносит актуальные хеши.

### Откат

```bash
ls -1dt /var/www/releases/flushot.ink-*
ln -sfn /var/www/releases/flushot.ink-<дата> /var/www/flushot.ink.new
mv -T /var/www/flushot.ink.new /var/www/flushot.ink
```

Откат — это та же самая операция переключения ссылки, поэтому занимает миллисекунды и не
требует перезапуска nginx.

## Конфигурация nginx

`/etc/nginx/conf.d/flushot.ink.conf` — три серверных блока: порт 80 перенаправляет на HTTPS,
порт 443 отдаёт сайт, отдельный блок на 443 перенаправляет `www` на основной домен.

Из поставки удалён штатный `default_server` (он отдавал `/usr/share/nginx/html`), иначе nginx
отказывался запускаться с ошибкой `a duplicate default server for 0.0.0.0:80`. Исходный файл
сохранён как `/etc/nginx/nginx.conf.bak-flushot`.

Что делает конфигурация, помимо очевидного:

- `try_files $uri $uri/ =404` — отдаёт файл, затем каталог, затем страницу 404. Без этого
  запрос `/` упирался бы в листинг каталога.
- `gzip` для текста: страница почти целиком текстовая, сжатие сжимает её с 51 до 11 КБ.
- Шрифты и картинки кэшируются на 30 дней (`immutable`), стили и скрипт — на 7 дней, а
  `index.html` не кэшируется вовсе. Иначе после деплоя браузер показывал бы старую страницу с
  новыми стилями.
- `server_tokens off` — не сообщает версию nginx.
- `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`,
  `Referrer-Policy` — в отдельном файле `/etc/nginx/flushot-security.conf`.

### Почему заголовки вынесены в отдельный файл

`add_header` в nginx не наследуется: если `location` объявляет **свой** `add_header`, он
забывает все заголовки серверного блока. Кэш-правила для картинок и стилей объявляют
`Cache-Control` — и без выноса HSTS и `nosniff` молча исчезали бы ровно у тех ответов, где они
нужнее всего. Поэтому `flushot-security.conf` подключается и в серверном блоке, и в каждом
`location`, который добавляет свой заголовок. Проверяется одной командой:

```bash
curl -sI https://flushot.ink/assets/hero.webp | grep -E 'Cache-Control|Strict-Transport'
```

Файлы отдаются с `immutable` на год, документ — с `no-cache`. Это безопасно только вместе с
хешем в ссылках (`npm run stamp`, см. «Почему ссылки на файлы содержат `?v=`»): без него
годовой кеш закрепил бы у посетителя устаревшую версию страницы.

Проверить и применить изменения:

```bash
nginx -t && systemctl reload nginx
```

## Домен

Домен `flushot.ink` куплен у Spaceship, DNS обслуживают серверы `launch1.spaceship.net` и
`launch2.spaceship.net`.

Нужны две записи в панели регистратора:

| Тип | Имя | Значение | TTL |
|---|---|---|---|
| `A` | `@` (или пусто) | `78.17.32.87` | 3600 |
| `A` | `www` | `78.17.32.87` | 3600 |

Если панель требует указать имя целиком, вместо `@` пишется `flushot.ink`, вместо `www` —
`www.flushot.ink`. Записи типа `AAAA` (IPv6) удалить или не создавать: у сервера IPv6 нет, и
браузер, выбравший IPv6, не смог бы открыть сайт.

Проверить, что мир видит новый адрес:

```bash
nslookup flushot.ink 1.1.1.1
curl -s -H 'accept: application/dns-json' \
  'https://1.1.1.1/dns-query?name=flushot.ink&type=A'
```

Обычно это занимает от нескольких минут до часа; TTL 3600 означает, что старый адрес может
держаться в кэшах до часа после правки.

**Важно:** на самом сервере в `/etc/hosts` уже прописано `78.17.32.87 flushot.ink` — это имя
хоста. Поэтому локальная проверка через `getent` или `ping` на сервере всегда показывает
правильный адрес и ничего не доказывает. Проверять нужно снаружи, как в командах выше.

## HTTPS

Сертификат Let's Encrypt выдан 22 октября 2026 и действует до 20 января 2027. Он покрывает
`flushot.ink` и `www.flushot.ink`.

Выпуск выполняется один раз, уже после того как домен указывает на сервер: проверка идёт по
публичному DNS, поэтому ранний запуск упирается в ошибку challenge и тратит попытку из лимита
Let's Encrypt.

```bash
ssh root@78.17.32.87
bash /root/issue-cert.sh
```

Скрипт сначала сверяет публичный DNS (через DNS-over-HTTPS, а не локальный `getent`) с адресом
сервера и останавливается, если они не совпадают. Затем `certbot` получает сертификат и сам
переписывает серверный блок.

Продление настроено: `certbot-renew.timer` включён, проверяет дважды в сутки и продлевает за 30
дней до истечения. Проверено командой `certbot renew --dry-run` — прогон успешный. Вручную
ничего делать не нужно.

Проверить:

```bash
certbot certificates
curl -sI https://flushot.ink | head -3
```

## Что где лежит

```
deploy/deploy-site.sh              выкладка сайта из репозитория
deploy/issue-cert.sh               выпуск сертификата
deploy/nginx/nginx.conf            главный конфиг nginx
deploy/nginx/flushot.ink.conf      серверные блоки сайта
deploy/nginx/flushot-security.conf заголовки HSTS и защиты
```

На сервере те же файлы лежат здесь:

```
/etc/nginx/nginx.conf              главный конфиг, штатный default_server удалён
/etc/nginx/conf.d/flushot.ink.conf серверные блоки сайта
/etc/nginx/flushot-security.conf   заголовки HSTS и защиты
/etc/nginx/nginx.conf.bak-flushot  исходный nginx.conf до правки
/etc/letsencrypt/live/flushot.ink  сертификат и ключ
/var/www/flushot.ink               символическая ссылка на текущий выпуск
/var/www/releases/flushot.ink-*    выпуски сайта, три последних
/root/deploy-site.sh               копия deploy/deploy-site.sh
/root/issue-cert.sh                копия deploy/issue-cert.sh
/var/log/nginx/flushot.access.log  журнал доступа
/var/log/nginx/flushot.error.log   журнал ошибок
```

## Проверка после выкладки

```bash
curl -sI https://flushot.ink | head -3                 # 200 и заголовки
curl -s -o /dev/null -w '%{http_code}\n' http://flushot.ink/   # 301
curl -sI https://www.flushot.ink | head -3             # 301 на без www
curl -s https://flushot.ink/robots.txt                 # карта сайта
```

Страница проверяется в настоящем браузере скриптом из проекта:

```bash
npm run verify:live
```

Он смотрит на три ширины экрана и сообщает про горизонтальную прокрутку, незагрузившиеся
шрифты, битые картинки, ответы 4xx/5xx и ошибки в консоли. Это важно именно для выкладки:
локальные проверки (`verify-site.cjs`) работают с файлами и не заметят, что сервер, например,
отдаёт не тот MIME тип.
